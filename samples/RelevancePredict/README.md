# Part 3: Predict

A runnable extension of the Part 2 console tool. It starts from empty SQLite storage, learns from generated observations and endpoints, predicts fresh journeys, and measures forecasts against a separate later population. The core library and its Markov predictor are the actual implementation, not a mock of their outputs.

```sh
dotnet run --project samples/RelevanceShop -- predict \
  --seed 814 --products 240 --train 1000 --test 400 \
  --output /tmp/relevance-predict-814
```

Or run this project directly: `dotnet run --project samples/RelevancePredict -- --output /tmp/relevance-predict-814`.

Use a new/empty output directory. The default database is a fresh owned temporary SQLite file, removed after the run. `--database /tmp/predict.db` keeps a new database; an existing database is rejected to prevent old training data contaminating a reproducibility run. The live outcome demonstration adds one final cancellation after the frozen benchmark, so the retained database includes that update.

The catalogue and users are invented with Bogus 35.6.5, independently seeded from the C# behaviour simulator. There is no real customer data. Fixed timestamps/clock and fixture version `bogus-shop-v2` make the numeric output repeatable. Engine-generated recommendation correlation IDs can differ between runs; they are not model parameters.

## What runs

- 240 products, 1,000 earlier training visits and 400 later holdout visits by default.
- Missing product descriptions, unavailable stock and censored/incomplete journeys are explicit.
- Prefix-only encoding retains comparison depth, first/repeated cart entry, basket removal and post-cart browsing. Hidden simulator intent and future outcomes are never input features.
- Incremental transition updates, minimum support, four-event destination forecasts and unresolved probability.
- SQLite close/reopen with an equality check on the learned forecast.
- Three fresh prefixes referencing the same product: identical relevant picks, different learned destination distributions.
- A frozen training-population snapshot for evaluation at the first-cart landmark. No held-out outcome is saved to the evaluator. Incomplete feedback is excluded from scoring rather than counted as failure; a fully observed horizon with no destination can be scored as unresolved.
- Multiclass Brier score against a training-only population prior, plus purchase reliability bins. Estimates remain marked uncalibrated.
- A live observed cancellation, duplicate retry and fresh checkout forecast demonstrating the next probability update directly.

The dataset's state vocabulary and simulator rules are explicit domain modelling. No automatic cluster discovery, neural network or model download is involved in the prediction run. In a real integration, use actual application events and explicitly defined endpoints.

## Artifacts

`--output` writes `catalogue.json`, `users.json`, `journeys.json`, `holdout.json`, `report.json`, `manifest.json`, `replay.json` and `output.txt`. These fixture files include complete synthetic journeys for inspection; the evaluator only ingests their observed prefixes. Do not replace that prefix boundary with a replay of complete held-out journeys before forecasting.

`PredictionReplay.CaptureAsync` uses a separate engine with frozen training counts to capture forecasts after every event of three fresh teaching visits and 21 generated holdout visits. The site's deck.gl destination explainer imports the checked-in `artifacts/seed-814/replay.json` directly; it never reconstructs likelihoods from plotted distances. To refresh it, run the article command and copy the generated `replay.json` into that artifact directory. The browser animates 24 distinct observed-state tracks, using an authored behavioural layout and separate display lanes. It retains unresolved probability in the inspector. Display coordinates are independent of forecasts; paths move backwards when the observed state returns to an earlier stage. Goal selection changes only utility, not forecasts. The capture uses a separate engine; displaying sampled holdout visits does not update the frozen population model or the benchmark.

[artifacts/seed-814](artifacts/seed-814) contains the actual console output, report, manifest and small readable catalogue/journey samples for the article. Full larger fixtures are generated by the command. Generated output files are not production accuracy evidence.

## Optional local LLM display copy

With Ollama running and an installed model:

```sh
python3 samples/RelevancePredict/generate-copy.py \
  /tmp/relevance-predict-814/catalogue.json /tmp/product-copy.json

dotnet run --project samples/RelevanceShop -- predict \
  --copy /tmp/product-copy.json --output /tmp/relevance-with-copy
```

The helper defaults to `qwen3.5:4b`; an optional third argument changes the model and a fourth changes the batch size (1–24). It does not download a model. The script freezes its response, exact prompt and host-supplied model provenance. Review the copy before importing it. A frozen six-product response from an actual local run is in [fixtures](fixtures).

The import contract permits only ID, name and description for known products. Unknown/duplicate IDs, unexpected properties and invalid text lengths are rejected. Prices, categories, stock, swatches, events and labels cannot be rewritten by the copy overlay. Descriptions are metadata in `predict.yaml`; changing them cannot alter the current model or ranking features.

To use the checked-in response without any model runtime:

```sh
dotnet run --project samples/RelevanceShop -- predict \
  --copy samples/RelevancePredict/fixtures/catalogue-copy.qwen3.5-4b.json \
  --output /tmp/relevance-frozen-copy
```

## Physical-time prediction

```sh
dotnet run --project samples/RelevanceShop -- predict-time --output /tmp/relevance-time-814
```

`TemporalPredictionDemo` starts fresh SQLite storage for shopping and incident domains. Each learns from 600 completed synthetic episodes with variable measurement timing and small feature noise. A separate later 300-visit population is forecast at its first motion-ready landmark against a frozen model. Missing feedback is unscored. The demo emits actual Brier scores against a training-only prior, then captures 24 visits per domain on their recorded UTC timelines.

The first three replay visits share the same current observation but differ in direction or pace. Their forecasts use the actual engine's fast centroid, velocity, acceleration and elapsed time, with a 60-second target window. The incident example seeds its normal reference from 40 earlier qualified healthy samples and never admits degraded observations. Its reference half-life is 24 hours, independent of the two-second live-centroid half-life.

Output: `temporal-shop-replay.json`, `temporal-operations-replay.json`, and `temporal-output.txt`. The article's captured versions live in `artifacts/seed-814`; the frontend imports them directly. Population models are frozen for evaluation/replay. The normal-reference bootstrap is sample infrastructure; ordinary integrations use the existing save/predict API and persisted store.

The statistical predictor uses bounded feature-cell centroids and observed destination frequencies. It has no neural model or separate retraining stage. These controlled simulator results do not establish production calibration, handle informative censoring automatically, or estimate intervention effects.
