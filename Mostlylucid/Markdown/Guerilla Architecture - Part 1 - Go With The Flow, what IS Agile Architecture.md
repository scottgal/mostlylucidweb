# Guerilla Architecture - Part 1 - Go With The Flow, what IS Agile Architecture? 

# Introduction
I admit I hesitated to create an ‘architecture’ series. I never truly considered myself an architect or what I might have assumed others were.  I wasn’t one for simply plugging together products and calling it architecture.  

For me the real rush wasn’t just designing the system but implementing its core.  It was immersing myself in that ‘flow’ where I generated functionality that made customers, end users and fellow developers happier. 

The odd consequence is I; despite having had over 2 dozen roles building software I only had an 'Architect' title when I was Technical Architect for VisitScotland, archotecting a J2EE system despite never having touched a line of Java before getting the gig. That really drove what I came to call 'guerilla architecture' - a rapid learning loop which needs you to form system design 'taste' beyond named patterns and established principles. 

['Agile Architecture' ](https://en.wikipedia.org/wiki/Agile_architecture)is sort of the overarching pattern. 

As you'll be aware 'Agile Architecture' as encodes in systems like SaFe has 6 main principles:

1. The teams that code the system design the system
2. Build the simplest architecture that can possibly work
3. When in doubt, code it out
4. They build it, they test it
5. The bigger the system, the longer the runway
6. System architecture is a role collaboration
7. There is no monopoly on innovation

Which, fair enough...and of course there's the 'Enterprise Extensions' for scale which includes 'have a team of dedicated enterprise architects' which is...well...interesting and not at all 'agile' .
